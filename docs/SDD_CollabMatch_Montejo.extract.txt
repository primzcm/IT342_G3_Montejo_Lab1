EXECUTIVE SUMMARY 
1.1 Project Overview 
CollabMatch is a collaboration platform that enables users to create project posts, find 
teammates, and manage collaboration requests. The system consists of a Spring Boot 
backend API, a React web application, and an Android mobile app, integrated to provide a 
seamless cross-platform experience. 
 
1.2 Objectives 
1. Develop a collaboration platform with authentication and project matching 
features. 
2. Implement a three-tier architecture using Spring Boot (backend), React (web), 
and Android (mobile) 
3. Create RESTful APIs for communication between all system components 
4. Design a responsive user interface that works consistently across web and mobile 
platforms 
5. Deploy all system components to production-ready environments 
 
1.3 Scope 
Included Features:  
● User registration and authentication (email/password) 
● User profile management 
● Create collaboration posts (project description + roles needed) 
● Browse and filter collaboration posts 
● Send join requests to projects 
● Approve or reject join requests 
● Dashboard for managing projects and requests 
● PostgreSQL database with Flyway migrations 
● React web interface 
● Android mobile application 
 
Excluded Features:  

===== PAGE 5 =====

● Real-time chat system 

===== PAGE 6 =====

● Video calls 
● Payment processing 
● Push notifications  
● Social media login integration 
● Advanced analytics dashboard

2.4 Detailed Feature Specifications 
Feature: User Authentication 
● Screens:  Registration, Login, Forgot Password 
● Fields: Email, Password, Confirm Password 
● Validation:  Email format, password strength, uniqueness 
● API Endpoints:  POST /auth/register, POST /auth/login, POST /auth/logout 
● Security:  JWT tokens, password hashing with bcrypt 
Feature: User Profile Management 
● Screens: Profile View, Profile Edit 
● Display: First Name, Last Name, Bio, Skills 
● API Endpoints: GET /users/{id}, PUT /users/{id} 
● Access Control: Users can only edit their own profile  
 
Feature: Collaboration Posts 
● Screens: Project Listing, Project Detail, Create Project 
● Fields: Title, Description, Category, Roles Needed 
● Display: List/Grid layout, Project title, short description, owner name 
● Search & Filter: By keyword, By category 
● API Endpoints: GET / projects, GET /projects/{id}, POST /projects, PUT 
/projects/{id}, DELETE /projects/{id} 
● Access Control: Only project owner can edit/delete their project 
 
Feature: Join Request System (Transactional Function) 
● Screens: Project Detail, Join Request Management 
● Functions: Send join request, Approve request, Reject request, View 
request status 
● Persistence: Stored in database with status (PENDING, APPROVED, REJECTED) 
● API Endpoints: POST /projects/{id}/requests, GET /projects/{id}/requests, PUT 
/requests/{id}/approve, PUT /requests/{id}/reject 
● Access Control: Only logged-in users can send requests, Only project owner 
can approve/reject requests

3.0 NON-FUNCTIONAL REQUIREMENTS 
3.1 Performance Requirements 
● API response time: ≤ 2 seconds for 95% of requests 
● Web page load time: ≤ 3 seconds on broadband 
● Mobile app cold start: ≤ 3 seconds 
● Support 100 concurrent users 
● Database queries complete within 500ms 
3.2 Security Requirements

 ● HTTPS for all communications 
● JWT token authentication 
● Password hashing with bcrypt (salt rounds = 12) 
● SQL injection prevention 
● XSS protection 
● Rate limiting: 100 requests/minute per IP

● Web Browsers:  Chrome, Firefox, Safari, Edge (latest 2 versions) 
● Android:  API Level 24+ (Android 7.0+)

● Operating Systems:  Windows 10+, macOS 10.15+, Linux Ubuntu 20.04+

minutes 
● Navigation should be consistent across web and mobile platforms 
● Clear validation error messages for incorrect inputs 
● Touch targets minimum 44x44px on mobile 
● Forms should provide real-time validation feedback 
● Users should be able to find a collaboration post within 3 clicks

6.0 DATABASE DESIGN 
6.1 Entity Relationship Diagram 
Note: This should be an ERD (Database Schema) 
Detailed Relationships:  

===== PAGE 15 =====

9 
 ● One-to-Many:  User → Projects (A user can create multiple projects)  
● One-to-Many: Project → JoinRequests (A project can receive multiple join 
requests) 
● One-to-Many: User → JoinRequests (A user can send multiple join requests) 
● Many-to-Many: Users ↔ Projects (Users can join multiple projects; projects can 
have multiple members) 
● One-to-Many: User → RefreshTokens (A user can have multiple active refresh 
tokens) 
Key Tables:  
1. users – User accounts and authentication 
2. projects – Collaboration posts created by users 
3. join_requests – Requests from users to join projects 
4. project_members – Approved project participants 
5. refresh_tokens  - JWT refresh tokens 
Table Structure Summary:  
● users: id, email, password_hash, username, role, created_at 
● projects: id, title, description, category, owner_id, status, created_at 
● join_requests: id, project_id, requester_id, status, message, created_at 
● project_members: id, project_id, user_id, joined_at 
● refresh_tokens: id, user_id, token, expiry_date
